# 14. 구조화 출력 — 환각을 "측정"에서 "형식 보장"으로

> 2026-10-14. 챗봇 응답을 자유 형식 마크다운에서 **후보 ID로 제한된 JSON**으로 바꿨다. 평가 하네스(`docs/12`)로 전후를 같은 조건에서 쟀다.

## 14.1 왜

평가 하네스로 "없는 식당 추천 0건"을 측정할 수는 있었지만 두 가지가 약했다.

1. **막은 게 아니라 잰 것**: 모델은 여전히 아무 이름이나 쓸 수 있었고, 0건은 그날 측정값일 뿐이었다.
2. **측정 자체의 오차**: 답에서 식당 이름을 휴리스틱으로 뽑았다. 추출기와 LLM 채점의 일치율이 0.91로, 9%는 무엇이 추천됐는지부터 불확실했다.

## 14.2 설계 (`frontend/api/chat.js`)

- **후보 ID**: 검색기가 고른 후보 40곳에 이번 요청에서만 쓰는 ID(`c1`..`c40`)를 붙여 프롬프트에 넣는다.
- **응답 스키마**: `{ intro, picks: [{ id, reason }], caveat }`. `picks[].id`는 이번 후보 ID의 `enum`이라 **목록 밖 식당은 형식상 나올 수 없다**. 최대 4곳이고 0곳도 허용한다.
- **`caveat`**: 데이터로 확인할 수 없는 요청(서울 밖 지역, 없는 메뉴, 유명인 추천 같은 전제)을 따로 받는 칸.
- **서버 재검증**: `enum`이 막아도 ID를 다시 검사해서 모르는 ID와 중복을 버리고 실제 식당 레코드로 바꾼다.
- **빈 약속 가드**: 추천이 0곳이면 `intro` 대신 `caveat`를 본문으로 쓴다 (14.3의 3번).
- **화면**: 마크다운 문자열 대신 메뉴판 줄(`상호 ........ ★평점`, 지역, 영업중, 이유)로 그리고, 누르면 상세 모달이 열린다. 전에는 `**` 같은 마크다운 기호가 그대로 보였다.
- **폴백**: JSON이 깨지는 드문 경우엔 예전처럼 본문에서 후보 이름을 찾는다.

## 14.3 실험하며 바꾼 것

1. **형식만으로는 "틀린 전제"를 못 막는다.** 규칙 없는 최소 프롬프트로 "성시경이 먹을텐데에서 극찬한 강남 오마카세"를 물었더니, 목록 밖 식당은 안 나왔지만 "성시경이 극찬한 맛집 후보 중…"으로 시작해 엉뚱한 곰탕집을 골랐다. 그래서 0곳 허용과 `caveat` 칸을 형식에 넣었다.
2. **"억지로 채우지 말라"는 규칙이 빈 약속을 만들었다.** 1차에서는 엣지 25문항 중 13건이 추천 0곳이었고, 그중 8건이 "서울 맛집을 대신 안내해 드립니다"라며 아무것도 주지 않았다. 모델은 대안을 주고 싶어 하는데 규칙이 막고 있었다. 규칙을 "대안이면 대안이라고 말하고 고를 수 있다, 하나도 없으면 약속하지 말라"로 바꾸자 2건으로 줄었다.
3. **지시로 안 되는 건 코드로 막았다.** 남은 2건은 서버 가드(추천 0곳이면 `caveat`를 본문으로)로 0건이 됐다.
4. **구조화 덕분에 채점기 버그를 찾았다.** 강북구 질문에서 매번 "지역 오답"이 나왔는데, 원인은 모델이 아니라 채점기였다. "조개일번지"가 두 곳(강북구 노포, 도봉구 야장)이고 채점기가 이름만으로 DB를 찾아 도봉구 집으로 판정했다. 데이터에 이런 동명 상호가 **34쌍(69곳, 6%)** 있다. 마크다운 답엔 주소가 없어 구분할 방법이 없었지만, 구조화 답은 주소가 오므로 이름+주소로 대조하게 고쳤다 (`eval/lib/data.mjs` `lookupByNameAddr`).

## 14.5 variance 측정과 LLM 점수 해석 (같은 날 추가 측정)

처음엔 "LLM 점수는 같은 프롬프트에서도 실행마다 ±0.3 움직여 비교할 수 없다"고 적었는데, **틀린 해석이었다.** 그때 비교한 두 실행은 프롬프트는 같았지만 빈 약속 가드 코드가 서로 달랐다. 같은 코드로 3회 반복(k=3, `eval/variance.mjs --from`)해서 다시 쟀다.

| 지표 (구조화 버전) | 실행별 값 | σ | 2σ |
|---|---|---|---|
| smoke 30: 환각 / 지역 / 카테고리 / 영업중 / 분류 불가 | 3회 모두 0 / 1.0 / 1.0 / 1.0 / 0 | 0 | 해상도 바닥 적용 |
| 엣지 25: LLM 의도 부합 | 3.04 · 3.20 · 2.84 | 0.15 | 0.29 |
| 엣지 25: LLM 유용성 | 3.64 · 3.72 · 3.60 | 0.05 | 0.10 |
| 엣지 25: LLM 정직성 | 1.0 · 1.0 · 1.0 | 0 | 0 |

k=3 표준편차는 거칠다. 가드 직전 실행(의도 3.36, 유용성 3.96)까지 넣은 k=4로 보면 의도 2σ 0.39, 유용성 2σ 0.28이다. 이 범위로 이전(마크다운, 1회) 대비를 다시 보면:

- **의도 부합 3.40 → 3.11**: 차이 0.29로 노이즈 범위 안. 달라졌다고 말할 수 없다. → **§14.6에서 정정**: 문항을 짝지어 비교하니 유의한 하락이었다.
- **유용성 4.08 → 3.73**: 차이 0.35로 2σ(0.28)를 넘는다. **떨어졌을 가능성이 높다.** 다만 이전 쪽은 1회라서 그쪽 편차는 모른다. → §14.6에서 마크다운도 3회 재고 짝지어 비교: 유의한 하락 확인.
- 문항별로 보면 한두 문항에 몰린 게 아니라 여러 문항에 퍼져 있다. 가장 그럴듯한 원인은 **답 본문이 덜 자세해진 것**이다. 마크다운 답에는 주소·영업시간·메뉴가 본문에 다 있었다. 구조화 답의 평문(`renderText`)은 이름·지역·이유뿐이고, 평점·영업중은 화면 카드에만 있다. 채점 모델은 평문만 보므로, "사용자에게 실제로 덜 유용한가"와 "채점기가 화면보다 적게 보는가"를 이 측정으로는 가를 수 없다.
- **채점 기준의 빈틈도 드러났다.** 마크다운 시절 엣지 답 25개 중 3개가 시스템 프롬프트를 그대로 읊었다. 규칙 문구를 따라 쓰거나(e02, e16), 후보 데이터의 원본 형식(`【오늘밤에포차】 | 지역: 강남구 | …`)에 "2~3곳을 골라 추천하자" 같은 혼잣말을 섞었다(e07). 그런데 LLM 채점은 e16에 유용성 5점을 줬다. 구조화 이후 225개 답에서 누출은 0건이다.

**CI 게이트 임계값** (`eval/variance.json`, smoke 3회): 규칙 지표는 3회 모두 같아 σ=0이다. 2σ=0을 그대로 쓰면 식당 하나만 다른 구로 골라도 CI가 떨어지므로, **측정 해상도(문항 하나가 움직이는 폭)를 바닥으로** 둔다: 지역 0.042(채점 24문항), 카테고리 0.125(8문항), 영업중 0.5(2문항), 분류 불가 0.033. 영업중은 채점 문항이 2개뿐이라 작은 회귀는 원래 못 잡는다는 사실을 그대로 드러낸다. **환각만 무관용**이라 바닥 없이 0이다.

**응답 시간**: 같은 코드에서 smoke p50이 4.8 · 1.7 · 1.6초(σ 1.5초)였다. 시간대에 따른 API 지연이 커서 이번 측정으로는 판단할 수 없다. 엣지는 1.66 · 1.60 · 1.69초로 안정적이었다.

## 14.6 원인 실험: 무엇이 유용성을 떨어뜨렸나 (2026-10-15)

가설은 "채점 모델이 화면 카드보다 적은 정보(평문)를 봐서"였다. 버전을 나눠 커밋하고 각각 엣지 25문항을 3회씩 쟀다 (생성·채점 모두 Lite, 버전별 git worktree로 실행, A와 B는 번갈아 실행해 시간대 효과를 상쇄).

| 버전 | 바뀐 것 |
|---|---|
| md | 마크다운 이전 버전 (어제 1회 + 오늘 2회) |
| S0 | 구조화 출력 초기 (어제 3회) |
| ① | 영업 판정 수정만 (서울 시각·브레이크타임) — 1회, 참고용 |
| A | ① + 평문에 카드와 같은 정보(지역·평점·영업중) |
| B | A + 카드·평문에 오늘 영업시간 |

**분석 방법을 바꿨다.** Gemini 503(과부하)으로 회차마다 문항의 약 20%가 빠져서, 회차 평균끼리 비교하면 문항 구성이 달라진다. 실제로 회차 평균 ±2σ 비교는 마크다운 쪽 편차(σ 0.19)가 커서 S0의 하락조차 "노이즈 경계"로 나왔다. 그래서 **모든 버전에서 채점된 19문항을 짝지어** 문항별 평균끼리 비교했다 (정확 부호 검정 + 문항 재표집 부트스트랩 95% CI).

| 마크다운 대비 (19문항 짝지음) | 유용성 | 의도 부합 |
|---|---|---|
| S0 구조화 초기 | **−0.52** [−0.81, −0.20], 3↑/14↓, p=0.013 | **−0.52** [−0.93, −0.11], 3↑/13↓, p=0.021 |
| A (+평문=카드) | −0.44 [−0.85, +0.01], 5↑/12↓ | −0.32 [−0.89, +0.27] |
| B (+오늘 영업시간) | −0.24 [−0.61, +0.11], **9↑/9↓** | −0.34 [−0.88, +0.12], 7↑/6↓ |

- **구조화 초기(S0)는 마크다운보다 유의하게 나빴다.** 유용성과 의도 부합 둘 다.
- **"채점기가 덜 봐서"는 거의 설명이 안 됐다.** 평문에 평점·영업중을 넣은 A는 S0 대비 +0.08(유의하지 않음).
- **구체 정보를 더한 B는 마크다운과 구분되지 않는다** (유용성 9↑/9↓). 마크다운 답이 높게 받던 이유는 형식이 아니라 영업시간 같은 구체 정보였던 것으로 보인다.
- **단 "B가 S0보다 낫다"고는 말하지 않는다.** B−S0 +0.28 [−0.12, +0.68]로 유의하지 않다. 19문항×3회로는 검정력이 모자란다. 말할 수 있는 건 "유의한 격차가 있던 상태에서, 구분되지 않는 상태가 됐다"까지다.
- **유지된 것**: 환각 0, 프롬프트 누출 0/225 (마크다운은 5/75).
- **채점 기준의 빈틈 하나 더**: B의 한 회차에서 "판교는 서울에 없지만, 대안으로 서울 맛집을…"이라고 사실대로 밝힌 답을 채점기가 "부정직"으로 판정했다. 근거는 "판교 대신 서울을 추천해 지역 조건에 맞지 않음"이었다. 정직성과 관련성을 섞어 보고 있다.
