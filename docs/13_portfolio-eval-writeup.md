## A. 노포지도 사이드프로젝트 — 추가할 섹션

### "RAG 품질을 어떻게 측정하는가" — 자동 평가 하네스

노포지도의 AI 맛집 추천은 Gemini 3.6 Flash에 식당 데이터(1,160곳)를 grounding해 답한다. "추천이 좋아졌다"를 감이 아니라 숫자로 말하기 위해 **재현 가능한 평가 파이프라인**을 직접 만들었다.

**골든셋 149문항** — data.json에서 층화 샘플링
- 서울 25개 구 균등(구별 최소 4문항) × 의도 6종(회식/혼밥/해장/데이트/부모님/늦은밤) × 카테고리
- **적대적 엣지케이스 25** 수기: 존재하지 않는 지역("서울 판교"), 데이터에 없는 메뉴(오마카세), 모순 조건("강남인데 홍대"), 0건 유도, 허위 전제("성시경 추천")

**이중 판정**
- *규칙 기반(결정적·무료)*: 답변에서 추천 식당명을 추출해 DB와 대조 → **실존하지 않는 식당 추천 = grounding 위반(환각)을 자동 검출**. 지역·카테고리·"지금 영업중" 일치도 규칙으로 채점(프로덕션 코드의 판정 함수를 그대로 재사용해 로직 드리프트 0).
- *LLM-as-Judge(Gemini)*: 규칙이 못 재는 의도 부합·유용성을 루브릭으로 채점(샘플링+해시 캐시로 비용 통제).

**측정 도구 자체를 신뢰할 수 있게 만든 장치** (이 프로젝트에서 가장 공들인 부분)
- **Negative control**: "환각률 0%"가 *탐지기가 잘 만들어진 것*인지 *아무것도 안 하는 것*인지 구분되지 않는다는 함정을 막기 위해, 일부러 위반을 심은 합성 응답으로 탐지기가 실제로 불이 켜지는지 검증(4/4). → **"0%가 진짜 0임을 증명"**.
- **고정 fixture 테스트**: 프롬프트를 바꾸면 응답 마크다운 포맷이 바뀌고 추출기가 조용히 깨져 점수가 "성능 변화가 아니라 계측기 고장" 때문에 움직인다. 손 라벨한 실제 응답 6종을 커밋해, 포맷이 바뀌면 지표보다 **이 테스트가 먼저 실패**하게 했다. (개발 중 실제로 추출 버그 2건을 이 테스트가 잡았다.)
- **Variance 측정(k=3)**: 같은 문항 세트를 3회 반복해 지표 편차(σ)를 재고, 회귀 게이트 임계값을 2σ로 **감이 아니라 데이터로** 정했다.

**CI 통합** — GitHub Actions(`eval.yml`)
- 매 PR: 규칙 판정·추출기 fixture·negative control은 **API 쿼터 없이 항상** 실행(계측기 건강 검사). 생성 eval은 키가 있을 때만, baseline 대비 **회귀 시 실패** + 결과를 PR 코멘트로.
- 프롬프트 A/B: 버전별 점수를 결과 파일로 분리 적재해 변화 추적.

> 스택: Node(프로덕션 chat.js의 grounding 로직 재사용, 새 의존성 0). 기존 배포 워크플로우는 불변.

**결과 스냅샷**: grounding 위반 0 · 지역 정확도 1.0 · 카테고리 1.0 · 영업중 1.0 (부분 실측). 추출기 fixture 6/6, negative control 4/4. → PR #1 5/5 checks passed.

### 환각을 "측정"에서 "형식 보장"으로 — 구조화 출력 (2026-10)

하네스로 "없는 식당 추천 0건"을 잴 수는 있었지만, 그건 그날의 측정값이었고 측정 자체에도 오차가 있었다(이름 추출기와 LLM 채점의 일치율 0.91). 그래서 답을 **후보 ID로 제한된 JSON**으로 받도록 바꿨다. `picks[].id`가 이번 후보 ID의 enum이라 목록 밖 식당은 형식상 나올 수 없다.

같은 하네스로 전후를 재며 찾은 것:
- **형식은 "없는 식당"만 막는다**: "성시경이 극찬한 강남 오마카세"에 모델은 목록 안 식당을 고르면서 그 전제를 사실처럼 받았다. → 0곳 허용 + `caveat`(데이터로 확인 불가한 요청) 칸을 형식에 넣음.
- **규칙이 만든 부작용을 지표로 잡음**: "억지로 채우지 말라"는 규칙이 "대신 안내해 드립니다"라고 하고 아무것도 안 주는 답을 25문항 중 8건 만들었다. 규칙 수정으로 2건, 마지막은 서버 가드로 0건. *지시로 안 되는 건 코드로 막는다.*
- **계측기 버그 발견**: 구조화 답에 주소가 오자, 채점기가 동명 상호 34쌍(69곳)을 이름만으로 판정해 다른 집으로 채점하던 버그가 드러났다. 이름+주소 대조로 수정.

결과(Lite, 같은 조건): 없는 식당 0건이 **형식으로 보장**, 분류 불가 답 1.2~1.5% → **0%**, 추출–채점 일치율 0.91 → **1.0**, 정직성 25/25 유지, 빈 약속 1 → **0**, 시스템 프롬프트 누출 3/55 → **0/225**.

**잃은 것도 숫자로 남겼다**: 같은 코드로 k=3 반복해 LLM 점수의 노이즈 폭을 잰 뒤 보니, 의도 부합 차이(−0.29)는 노이즈 범위 안이었지만 **유용성은 4.08 → 3.73으로 2σ(0.28)를 넘게 떨어졌다**. 답 본문에서 주소·영업시간이 빠져 덜 자세해진 게 유력한 원인이다 — 다음 측정에서 본문 정보를 화면과 맞춰 원인을 가린다. 처음엔 "실행마다 ±0.3 출렁여 비교 불가"로 결론냈다가, 그 두 실행이 코드가 달랐음을 알고 반복 측정으로 정정했다. (상세: `docs/14`)

## B. 뉴로코어 케이스 스터디 회고 — 갱신할 문단

**기존 회고**: "응답 정확도 +30%는 평가셋 10문항 기준이라 통계적 신뢰도가 약했다. 다시 한다면 LLM-as-Judge로 70%를 자동화하겠다."

**갱신(추가)**:
> 그 회고를 말로 남기지 않고 실제로 구현했다. 사이드프로젝트 노포지도의 RAG 챗봇에 대해, 149문항 골든셋 + 규칙/LLM 이중 판정 + CI 회귀 게이트를 갖춘 평가 하네스를 만들었다([코드](https://github.com/hizieun/noodle-app/tree/main/eval)).
>
> 특히 뉴로코어에서 놓쳤던 두 가지를 정면으로 보강했다:
> 1. **표본 크기·유의성** — 10문항의 +30%가 통계적으로 유의한지 답할 수 없던 것이, 이번엔 같은 세트를 k회 반복해 지표의 표준편차를 측정하고 회귀 임계값을 2σ로 데이터에 근거해 정하는 구조로 바뀌었다.
> 2. **측정 도구의 신뢰성** — "정확도가 올랐다"는 숫자가 계측기 고장이 아님을 어떻게 아는가? Negative control(합성 위반으로 탐지기 검증)과 고정 fixture(프롬프트 포맷 변경 시 지표보다 먼저 실패)로, 지표가 움직일 때 그것이 성능 변화임을 보증했다.

## C. 면접 예상 질문 → 답변 자산

- **"RAG 품질을 어떻게 측정하나?"** → 규칙(grounding/지역 결정적 검증) + LLM-Judge(의도부합) 이중 판정, 149 골든셋, CI 회귀 게이트. 코드로 시연.
- **"환각을 어떻게 잡나?"** → 답변 상호명을 추출해 실데이터와 대조. 헤더 휴리스틱으로 추천/제외를 구분(순수 substring은 "제외 언급"을 오탐).
- **"그 탐지기가 실제로 작동하는지는 어떻게 아나?"** → Negative control. 일부러 위반을 심어 탐지기가 켜지는지 검증한다. 0%가 진짜 0임을 증명.
- **"프롬프트를 바꾸면 평가가 깨지지 않나?"** → 고정 fixture 테스트가 계측기 고장을 지표보다 먼저 잡는다. + unclassified 버킷으로 추출기 신뢰도 모니터링.
- **"몇 %p 움직여야 회귀인가?"** → variance k=3의 2σ. 감이 아니라 데이터.
- **"환각을 막았나, 측정만 했나?"** → 응답을 후보 ID enum으로 제한한 구조화 출력으로 *없는 식당*은 형식상 불가능하게 했다. 단 형식은 *틀린 전제*는 못 막아서(실험으로 확인) 0곳 허용 + caveat 칸을 따로 설계했다.
- **"LLM 점수가 올랐다는 근거는?"** → 오르지 않았다. 같은 코드로 k=3 반복해 노이즈 폭(2σ)을 먼저 재고 비교했더니, 의도 부합은 노이즈 범위 안이고 유용성은 오히려 2σ를 넘게 떨어졌다. 개선으로 말하는 건 결정적 지표(형식 보장·일치율 1.0·빈 약속 0·프롬프트 누출 0)뿐이고, 유용성 하락은 원인 가설과 함께 다음 실험으로 남겼다.
- **"그 2σ는 믿을 만한가?"** → k=3이라 거칠다(가드 직전 실행을 더한 k=4로 보면 2σ가 0.10→0.28로 커진다). 그래서 넓은 쪽(k=4) 기준으로 판단했다. 또 늘 1.0인 규칙 지표는 σ=0이 나오는데, 이건 노이즈가 없다는 뜻이 아니라 구분을 못 한다는 뜻이라 게이트 임계값에 '문항 하나 폭' 바닥을 뒀다(환각만 무관용 0).
- **"LLM 채점은 믿을 만한가?"** → 빈틈을 하나 찾았다. 시스템 프롬프트를 그대로 읊은 답에 유용성 5점을 줬다. 그래서 결정적 지표와 LLM 점수를 분리해서 보고, 채점 기준에 누출 감점을 추가할 예정.
